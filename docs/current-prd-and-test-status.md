## 1. 제품 정의

갈래는 단순 최단경로 추천기가 아니다.

목표 도착시간을 기준으로 출발 전부터 이동 중까지 실시간 상황을 반영해 경로를 재판단하는 개인화 이동 비서다.

핵심 질문은 다음이다.

> 사용자가 늦지 않으면서 가능한 늦게 출발하려면, 지금 어떤 경로를 선택하고 언제 움직여야 하는가?

## 2. 핵심 원칙

### 2.1 Plan은 고정하고, Realtime은 확인한다

필드테스트에서 가장 크게 확인된 문제는 realtime이 갱신될 때마다 사용자가 선택한 계획까지 흔들렸다는 점이다.

따라서 선택 전과 선택 후를 분리한다.

| 상태 | 목적 | 동작 |
| --- | --- | --- |
| 경로 선택 전 | 후보 비교 | 현재 realtime과 시간표를 이용해 후보별 ETA를 비교 |
| 경로 선택 후 | 선택 계획 확인 | 선택 당시 계획을 유지하고 realtime은 이행 가능 여부 확인에만 사용 |

선택 후 화면은 최신 추천으로 계속 바뀌면 안 된다.  
선택 당시 열차, 출발시각, 환승, ETA를 보존해야 한다.

### 2.2 Realtime freshness는 ETA보다 선행조건이다

stale realtime은 판단 입력으로 사용하지 않는다.

stale 데이터는 다음에 사용하면 안 된다.

- LIVE 표시
- ETA 계산
- plan deviation 계산
- 추천 근거
- fallback 판단

8/26 테스트에서 12:55 조회 시 12:34 snapshot이 LIVE처럼 보인 문제가 있었고, 이 이후 freshness는 P0 조건으로 격상됐다.

### 2.3 동일 열차 매칭보다 사용자 계획 편차가 중요하다

v0.1에서는 철도 운영상 동일 열차를 식별하는 것보다 사용자 관점의 계획 편차를 우선한다.

예:

- 계획: 독산역 12:37 탑승
- 현재 이용 가능: 독산역 12:45 탑승
- 판단: `plan_deviation +8분`

이 편차는 다음 연결편, 최종 ETA, deadline 판단에 전파되어야 한다.

### 2.4 데이터 우선순위

판단 데이터 우선순위는 다음과 같다.

1. realtime
2. schedule/plan
3. estimate

서해선 일부 구간처럼 실시간 데이터가 확인되지 않은 구간은 v0.1에서 schedule/plan fallback을 사용한다.  
단, fallback을 LIVE처럼 표시하면 안 된다.

## 3. v0.1 지원 범위

### 3.1 목적지 정의

문서와 v0.1 테스트에서 “시흥”, “시흥센터”는 시흥여성인력개발센터를 의미한다.

시흥대야역은 2026-09-07 기준 기존 PoC 모델의 정식 목적지로 반영되어 있지 않다.  
따라서 시흥대야역 이동에서 기존 PoC ETA를 신뢰하면 안 된다.

### 3.2 이동 방향

v0.1에서 우선 지원한 방향:

- 집 → 시흥
- 시흥 → 집

방향 선택은 UI 표시만 바뀌는 것이 아니라 다음 판단 데이터가 함께 바뀌어야 한다.

- 출발지 / 목적지
- 후보 경로
- realtime 조회 대상
- ETA
- deadline 판단
- fallback
- 버스 추천 방향

### 3.3 후보 경로

#### 집 → 시흥

주요 후보:

- 금천07 → 가산디지털단지역 → 7호선 석남 방향 → 부천종합운동장 → 서해선 → 신천 → 시흥센터
- 독산역 → 1호선 → 구로 → 소사 → 신천 → 시흥센터

#### 시흥 → 집

우선 확인한 후보:

- 신천 → 부천종합운동장 → 7호선 → 가산디지털단지역 → 금천07 → 집
- 1호선 귀가 ETA는 구현·검증 필요 항목으로 남음

## 4. ETA 계산 요구사항

### 4.1 기본 목표

목표 도착시간을 기준으로 각 후보 경로의 도착 ETA를 계산한다.

사용자가 원하는 것은 가장 빠른 도착이 아니라:

> 목표 도착시간에 늦지 않는 범위에서 가장 늦게 출발하는 경로

따라서 추천 정렬은 단순 ETA 빠른순이 아니다.

권장 판단:

1. 목표 도착시간을 넘지 않는 후보를 우선
2. 그중 목표시각에 가장 가까운 후보를 우선
3. 충분히 여유가 있으면 안정성/환승 부담/사용자 선호를 반영
4. 목표 또는 마감시각 초과 예상 시 지각 최소화를 우선

### 4.2 최소 환승시간

기존 문제:

- `nextConnection()`이 현재 도착 직후 첫 연결편을 선택
- 1초~1분 환승도 가능한 것으로 판단

수정 원칙:

- `currentArrival + MIN_TRANSFER_MINUTES` 이후 출발하는 연결편만 선택
- 기본 최소 환승시간은 3분

8/24 문서 기준으로 `rolling-eta.js`는 최소 환승시간 3분 강제 수정이 완료된 것으로 기록되어 있다.  
단, 실제 운영 데이터에서 계속 검증해야 한다.

### 4.3 구간별 계산 방식

| 구간 | v0.1 계산 방식 | 상태 |
| --- | --- | --- |
| 집 → 금천07 → 가산 | 버스 실시간 + 고정 접근 추정 혼합 | 부분 검증 |
| 가산 → 부천종합운동장 | 7호선 realtime 또는 계획 구간 | 7호선 API 확인됨 |
| 부천종합운동장 → 신천 | 서해선 공식 시간표 | 실시간 보류 |
| 독산 → 구로 | 1호선 realtime | freshness 이슈 있음 |
| 구로 → 소사 | schedule/plan | fallback |
| 소사 → 신천 | schedule/plan | fallback |
| 신천 → 시흥센터 | 고정 최종 접근 추정 | estimate |

## 5. Realtime freshness 기준

### 5.1 필요한 필드

각 realtime 응답은 최소 다음 정보를 가져야 한다.

- `requested_at`
- `observed_at`
- `age_seconds`
- `freshness`
- `realtime_usable`

### 5.2 현재 확인된 상태

#### 7호선 가산디지털단지역

확인된 사실:

- Vercel `/api/subway`에서 가산디지털단지역 7호선 원응답 확인
- 석남 방향 데이터 수신 확인
- freshness 필드 확인
- 2026-09-07 확인 당시 API 자체는 정상, fresh, `realtime_usable: true`

주의:

- Pages UI에서 실제 사용자 조회시각과 원응답 freshness가 일치하는지는 별도 검증 조건이다.
- API 성공만으로 Pages 검증 완료로 보지 않는다.

#### 1호선 독산역

확인된 사실:

- Vercel `/api/doksan`에서 독산역 1호선 원응답 수신
- 2026-09-07 확인 당시 응답은 있었지만 `age_seconds`가 60초 threshold를 초과해 stale 처리됨
- 이 경우 ETA/추천 근거로 사용하지 않는 것이 맞다

남은 문제:

- threshold 60초가 실제 1호선 API 특성에 적절한지 추가 검증 필요
- stale row는 확인용으로 보여줄 수 있으나 ETA에는 사용하면 안 됨

## 6. 버스 데이터 요구사항

### 6.1 금천07 집 → 가산

확인된 상태:

- ARS 18514에서 금천07 실시간 데이터 수신
- 사용자 이동경험 기준으로 집 → 가산 접근에 사용

주의:

- 공식 노선·정류장 순서 검증은 후속 필요
- UI에는 `사용자 이동경험 근거, 공식 노선순서 후속 검증 필요`로 구분해야 한다
- 18514에 320안산이 섞이는 문제는 정류장 identity/source/mapping 순서로 추적해야 한다

### 6.2 금천07 시흥 → 집

확인된 상태:

- 18603 승차 → 18859 하차 기준
- 공식 노선순서 검증된 방향으로 기록됨

### 6.3 UI 표시

버스 도착시간은 상대시간만 표시하지 않는다.

예:

```text
4분 뒤 (07:16)
```

내부 evidence에서는 다음을 구분한다.

- API가 직접 제공한 시각
- 현재시각 + 도착예정분으로 계산한 시각

### 6.4 경로별 버스 카드 필터링

확정 경로가 독산 1호선이면 가산 연결 버스 카드를 보여주면 안 된다.

현재 확인된 수정:

- 독산 1호선 경로 확정 시 가산 버스 카드 숨김
- 가산 7호선 경로 확정 시 금천07 카드 표시

## 7. UI/UX 요구사항

### 7.1 사용자가 이해할 수 없는 표현 제거

제거 또는 수정 대상:

- `반대방향`
- `fallback`
- `rolling`
- `deviation`
- `freshness`
- `UNUSABLE` 단독 표시

권장 표현:

| 내부 표현 | 사용자 표현 |
| --- | --- |
| fallback | 대체 경로 |
| rolling recommendation | 최신 후보 |
| selected journey | 확정한 경로 |
| plan deviation | 계획과 달라짐 / 예정보다 지연 |
| freshness | 실시간 정보 최신 여부 |
| stale | 오래된 정보 / 최신 정보 아님 |
| unusable | ETA 판단에 사용할 수 없음 |

### 7.2 목표 도착시간 중심 UI

사용자에게 중요한 것은 절대 마감시각보다 목표 도착시간이다.

v0.1 UI에서는 목표 도착시간을 중심으로 유지하고, 절대 마감시각은 내부 판단값 또는 v0.2 이후 UX로 분리한다.

향후 v0.2 아이디어:

- 목표 도착시간 입력
- 10분 전 / 20분 전 / 30분 전 도착 선호 선택
- 내부에서 마감·여유시간 역산

### 7.3 경로 확정 전/후 화면

#### 경로 확정 전

- 후보별 ETA 비교
- 후보별 realtime 최신 여부 표시
- 자동 확정하지 않음
- 사용자가 `이 경로 확정` 버튼으로 선택

#### 경로 확정 후

- 확정한 경로만 중심 표시
- 다른 노선 realtime 카드는 숨김
- 선택 당시 계획과 현재 상태를 분리 표시
- 실시간은 계획 교체가 아니라 이행 가능 여부 확인용

## 8. selected journey 상태 모델

필요 필드:

- `direction`
- `route_id`
- `selected_at`
- `selected_journey_status`
- `current_leg_index`
- `planned_departure`
- `planned_eta`
- `planned_train`
- `planned_transfers`
- `target_arrival_time`
- `deadline_time` 또는 내부 margin 기준
- `recovery_count`
- `current_status`
- `next_available_service`
- `recalculated_eta`
- `plan_deviation_minutes`
- `evidence`

권장 상태:

| 상태 | 의미 |
| --- | --- |
| `browsing` | 후보 비교 중 |
| `committed` | 계획 확정, 정상 진행 중 |
| `deviated` | 선택 계획과 실제 상황이 달라짐 |
| `alternative_offered` | 대체 경로 제안 중 |
| `done` | 완료 또는 종료 |

`이 경로 종료` 같은 버튼은 사용자에게 노출하지 않는다.  
종료는 내부 상태 판단으로 처리한다.

## 9. 놓침/복구 로직

선택한 열차를 놓쳤는지는 사용자 질문으로 확인할 수 있다.

권장 질문:

```text
선택한 열차를 탔나요?
[탔어요] [놓쳤어요] [아직 확인 중]
```

복구 순서:

1. 선택한 계획 이행 가능 여부 확인
2. 놓쳤거나 이용 불가하면 같은 경로 안에서 다음 교통편 탐색
3. 새 ETA 계산
4. 목표 도착시간/margin 판단
5. margin이 위험하면 대체 경로 비교

추가 필요:

- `recovery_count` 상한 명시
- 확인 대기 상태 timeout 정책

임시 권장:

- 같은 경로 복구 2회 초과 또는 목표 도착 margin이 caution 이하이면 대체 경로 비교

## 15. 현재 기준 결론

갈래 PoC의 핵심 실패는 단일 API 연결 실패가 아니다.

핵심 문제는 다음 세 가지다.

1. 사용자가 선택한 계획이 realtime 갱신에 의해 흔들림
2. stale realtime이 LIVE/ETA 판단에 섞일 위험
3. 코드 작성, 배포, 실제 Pages/현장 검증이 분리 관리되지 않음

따라서 다음 개발은 새 기능 추가보다 먼저 다음을 안정화해야 한다.

- Plan 고정
- Realtime freshness
- 경로별 UI 필터링
- 실제 Pages 검증 루프
- 목표 도착시간 기준 ETA 판단
